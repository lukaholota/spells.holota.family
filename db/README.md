# db/

База даних — джерело істини. Тут лежить те, що з неї виводиться, і журнал того, що в неї вносили.

Обґрунтування — [docs/DECISIONS.md → Р2](../docs/DECISIONS.md#р2-бд--джерело-істини-міграцій-немає).

## Воркфлоу

```
пишеш SQL → застосовуєш на базі → bun run db:pull → коміт
```

`prisma/schema.prisma` — **згенерований артефакт**. Руками не редагується ніколи.

## Що тут лежить

| | Що це | Хто оновлює |
|---|---|---|
| `changes/` | журнал застосованого SQL | людина, руками |
| `schema.sql` | `pg_dump --schema-only` — піднімає порожню базу для CI | `bun run db:pull` |

`db:dump` і `db-clone.sh` потребують клієнта Postgres не старшого за сервер (зараз 16).
Шукати придатний бінарник уміє `scripts/lib/pg.sh` — навіть якщо його немає в `PATH`, як буває
з unlinked `postgresql@16` у Homebrew. Якщо не знайде — скаже, що поставити.

## `changes/` — це журнал, а не міграції

Файли тут **не програються автоматично**, не мають порядку застосування і не мають відкату.
Вони існують, щоб через півроку можна було подивитись, що саме робили з базою і чому.

Ім'я: `YYYY-MM-DD-короткий-опис.sql`.

Кладемо рівно той SQL, який реально виконали. Якщо після застосування щось довелось доправити —
доправляємо файл, а не додаємо другий.

## Правила

- **Ніякого `prisma db push`.** Він сам вирішує, що дропнути, і робить це мовчки.
- **Ніякого `prisma migrate`.** Див. Р2.
- SQL проти прода виконує **власник**, не агент. Агент готує скрипт і віддає.
- Усе в одній транзакції (`BEGIN` / `COMMIT`).
- У скриптах, що видаляють дані, — перевірка на порожнечу перед видаленням (приклад:
  [2026-08-07-drop-legacy-flask-tables.sql](changes/2026-08-07-drop-legacy-flask-tables.sql)).

## Клонування бази

```bash
./scripts/db-clone.sh spells_test              # схема + контент, без даних користувачів
./scripts/db-clone.sh spells_staging full      # усе
./scripts/db-clone.sh spells_scratch schema    # тільки структура
```

Цільова база мусить закінчуватись на `_test` / `_staging` / `_dev` / `_scratch` — інакше скрипт
відмовиться. Це щоб прод було неможливо затерти.

## Тестова база

`spells_test` піднімається тим самим скриптом і використовується тестами
([KR1.3](../docs/o1-safety-net/kr1.3-test-database.md)):

```bash
./scripts/db-clone.sh spells_test     # скрипт друкує DATABASE_URL у кінці
```

Далі цей URL кладеться в `.env.test` у корені. Файл **у git не потрапляє** (`.env*` в `.gitignore`),
тож на новій машині його треба створити руками — `tests/setup.ts` про це скаже, якщо файл відсутній.

Значення обов'язково **в подвійних лапках**: у URL є `&`, і без лапок ламається `source` у
`scripts/lib/pg.sh`, а падіння виглядає як «локальний сервер не запущено» — вказує зовсім не туди.

```
DATABASE_URL="postgresql://…/spells_test?schema=public&connect_timeout=30&pool_timeout=30"
```

Тести роблять `TRUNCATE` таблиць користувача, тому `tests/setup.ts` відмовляється працювати з
базою, чиє ім'я не закінчується на `_test`. Оточення має пріоритет над `.env.test` — це те саме
правило, що в `load_dotenv`, і саме воно дозволить CI подавати URL змінною.
