# O3 — Рушій правил

**Мета:** дістати математику D&D з серверних екшенів у чистий детермінований код.

## Куди йдемо

```
зараз:   createCharacter (1276 рядків) = валідація + запити + правила + записи

після:   src/lib/actions/character.ts   ← тонкий: завантажив → викликав → зберіг
         src/rules/                     ← чистий, без Prisma, без next, без I/O
         src/server/db/                 ← єдине місце, де є prisma.*
```

Головний критерій: **`src/rules/` можна тестувати без бази взагалі.** Вхід — білд плюс потрібний
контент, вихід — похідний лист персонажа. Жодних `await` до Postgres усередині.

## Правила цього етапу

**1. Один екшен за раз, один PR.** Не «перепишемо все і подивимось». Після кожного PR golden-файли
з O2 зелені без жодної правки.

**2. Golden-файл зачервонів → зупинись і прочитай дифф.** Оновлювати його «щоб стало зелено» —
це знищити весь сенс O2. Якщо зміна навмисна, вона йде окремим комітом із поясненням.

**3. Не виправляти баги по дорозі.** Спокуса буде на кожному кроці. Виправлення поведінки й зміна
структури в одному коміті означає, що при регресії неможливо зрозуміти, що саме її спричинило.
Баги з [KNOWN-BUGS.md](../KNOWN-BUGS.md) виправляються **після** того, як відповідний шматок
переїхав у `src/rules/` — там це рядок у чистій функції з тестом навколо.

**4. Перейменування — теж зміна.** `Character*` і `Pers*` в коді означають одне й те саме. Звести
до `Pers` варто, але окремими механічними комітами, не змішуючи з перенесенням логіки.

## Чому саме в такому порядку

KR3.1 перший, бо решта в нього переїжджає. KR3.2 перед KR3.3, бо створення простіше за левелап
(рахує з нуля, а не змінює наявний стан). KR3.4 останній із структурних, бо межу БД видно тільки
тоді, коли ясно, що саме правилам потрібно на вході. KR3.5 і KR3.6 — вимірювальні, закриваються
в кінці.
