# KR2.2 — Golden-файли створення персонажа

**Ціль:** [O2](README.md) · **Статус:** ✅ зроблено 2026-08-13 · **Залежить від:** KR2.1

## Навіщо

`createCharacter` — 1276 рядків, у яких перемішані валідація, читання з БД, математика правил і
записи. Розібрати це в O3 без сітки неможливо. Golden-файл — і є сітка: він фіксує, що на виході
з тієї самої матриці білдів виходить байт-у-байт той самий персонаж.

## Готово, коли

- [x] для кожного білда з KR2.1 є `tests/golden/creation/<build-id>.json`
- [x] тест ганяє `createCharacter` і порівнює **весь** збережений стан персонажа з файлом
  (Pers-скаляри, раса/підраса/варіант/клас/підклас/походження, features, feats+вибори, skills,
  зброя, броня — `tests/helpers/normalize-golden.ts`)
- [x] нестабільні поля нормалізуються — **уточнення 2026-08-13**: не перенумерацією id, а тим, що
  `tests/user-data.ts` робить `TRUNCATE ... RESTART IDENTITY` перед кожним тестом і кожен тест
  створює рівно одного користувача й одного персонажа. Тому persId/userId і всі дочірні автоінкременти
  завжди та сама детермінована послідовність — окрема логіка перенумерації виявилась зайвою
- [x] прогін детермінований: двічі поспіль — 34/34 байт-у-байт однаково
- [x] `bun run test:golden:update` перегенеровує файли (`UPDATE_GOLDEN=1 vitest run tests/golden`),
  і це усвідомлена дія (окрема команда), а не побічний ефект звичайного `bun run test`

## Що саме знімати

**Не** те, що повернув екшен. Те, що **лягло в БД** — включно зі зв'язками:

- рядок `Pers` цілком
- `PersSkill`, `PersFeature`, `PersSpell`, і решта `Pers*`
- обчислені величини: характеристики після всіх бонусів, HP, AC, бонус майстерності,
  рятівні кидки, слоти заклинань (стандартні й пактові), використання фіч

Читаємо після запису одним запитом із повним `include`, серіалізуємо зі стабільним сортуванням
(інакше порядок рядків з Postgres плаватиме і тести будуть блимати).

## Нормалізація

```ts
function normalizeForGolden(state) {
  // id → послідовні 1..n у порядку сортування, не з БД
  // дати → фіксована мітка
  // масиви → відсортовані за стабільним ключем
}
```

Замінювати id на `null` — погана ідея: тоді тест не побачить, що зв'язок з'єднався не з тим
рядком. Треба саме перенумерація.

## Правила читання диффа

Коли golden червоніє під час O3 — це **не** «тест зламався». Це одне з двох:

1. **Рефакторинг змінив поведінку** → баг у рефакторингу, виправляти код;
2. **Зміна навмисна** (виправили баг із KNOWN-BUGS) → оновити файл **окремим комітом**,
   у повідомленні написати, який саме баг виправлено.

Оновлювати golden-файли «щоб стало зелено», не прочитавши дифф — це знищити весь сенс етапу.

## Журнал

**2026-08-13.** `createCharacter` не приймає сесію напряму — читає її через `auth()` з
`@/lib/auth`, і викликає `revalidatePath` з `next/cache`. Обидва непридатні поза Next-раннером,
тож харнес мокає обидва модулі (`vi.mock`) і підставляє сесію реального тестового користувача
через `vi.mocked(auth).mockResolvedValue(...)`. Раніше в проєкті жоден серверний екшен так не
тестувався — це перший приклад патерну, наступні server-action тести можуть копіювати підхід.

Побічний ефект: додавання другого DB-тестового файлу (на додачу до `tests/database.test.ts`)
зробило `bun run test` нестабільним — Vitest за замовчуванням ганяє файли тестів паралельно, і
обидва файли труncatять ту саму `spells_test` між своїми тестами. Виправлено `fileParallelism:
false` у `vitest.config.mts` — деталі в журналі [KR2.1](kr2.1-build-matrix.md).

Перевірено, що харнес реально ловить регресію (не лише зелений з першого прогону): зіпсував
значення в одному golden-файлі руками, прогін почервонів з очікуваним діффом, повернув назад —
знову зелено.
