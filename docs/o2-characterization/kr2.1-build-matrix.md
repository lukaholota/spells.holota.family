# KR2.1 — Матриця білдів

**Ціль:** [O2](README.md) · **Статус:** ✅ зроблено 2026-08-13 · **Залежить від:** KR1.3

## Навіщо

Golden-тести варті рівно стільки, скільки покриває набір вхідних даних. Треба свідомо обраний
набір білдів, який зачіпає кожну гілку логіки створення персонажа — а не «десяток тих, що першими
спали на думку».

## Готово, коли

- [x] `tests/fixtures/builds/` — кожен білд це файл із валідним `PersFormData`
- [x] покрито всі осі з таблиці нижче (у скоригованому вигляді — див. журнал)
- [x] кожен білд має поле `why`: **чому саме він у наборі**, яку гілку тримає
- [x] набір проганяється через `createCharacter` без помилок (сам результат — KR2.2, `tests/golden/creation.test.ts`, 34/34 зелені двічі поспіль)

## Осі покриття

Мінімум по одному білду на кожне значення. Комбінувати осі, де вони взаємодіють.

| Вісь | Значення |
|---|---|
| Клас | усі 13 (`Classes` enum має `ARTIFICER_2014` — 12 PHB-класів + Артифайсер, TCE/Eberron, уточнено 2026-08-13) |
| Тип кастера | повний, половинний, третинний, пактовий, некастер |
| Підклас | береться на 1, 2, 3 рівні (залежить від класу — 2014!) |
| Система ASI | `POINT_BUY`, `SIMPLE`, `CUSTOM` |
| Раса | з фіксованим ASI, з ASI на вибір (Tasha), з підрасою, з варіантом раси |
| Варіант раси | `overridesRaceASI` виставлений і ні |
| Підраса | `replacesASI` виставлений і ні |
| Походження | з рисою і без |
| Риса | без риси, `Variant Human`, риса з вибором (Resilient, Skill Expert, Fighting Initiate) |
| Опції класу | клас з `ClassChoiceOption` і без |
| Експертиза | є / немає |
| Мови | вибір є / немає |

**Мультиклас прибрано з осей 2026-08-13.** `createCharacter` завжди створює персонажа 1 рівня з
одним класом (`multiclasses: []` — жорстко зашито, `character.ts:847`). Мультиклас з'являється
лише через левелап. Ця вісь і вся мультикласова комбінаторика — предмет
[KR2.3](kr2.3-golden-levelup.md) (левелап), не цього KR. Розвідка це підтвердила: KR2.1 не має
жодного шляху змусити `createCharacter` створити мультиклас-персонажа.

## Особливі випадки, які треба покрити явно

Це місця, де за словами власника вже щось ламалось або де логіка найзаплутаніша.

**Уточнено 2026-08-13** розвідкою по коду (`character.ts`): три з чотирьох пунктів нижче
виявились не про KR2.1 — переносяться туди, де вони реально відбуваються.

- **Warforged** — `initialRaceStaticAcBonus` у `createCharacter` (character.ts:189-192) це
  **жорстко зашитий літерал `0`**, а не гілка, що читає `race.ac.consistentBonus`. **Перевірено
  2026-08-13, це НЕ баг**: є окрема дія `updateRaceStaticAcBonus` (equipment-actions.ts:284-303) і
  тумблер на аркуші персонажа (`CombatSlide.tsx`) — гравець вмикає бонус вручну після створення.
  `createCharacter` коректно лишає його вимкненим на старті. У KNOWN-BUGS НЕ заноситься.
  Природна броня за расою (Tortle, Monk/Barbarian unarmored defense) — окремий, реальний ризик,
  див. наступний пункт.
- ~~Мультикласові слоти заклинань — повний + пактовий разом~~ → [KR2.3](kr2.3-golden-levelup.md),
  недосяжно з `createCharacter`.
- ~~Four Elements Monk — дисципліни~~ → надаються від 3 рівня через левелап
  (`choicePoolRules.ts:102-104`), недосяжно з `createCharacter` → [KR2.3](kr2.3-golden-levelup.md).
- ~~Артифайсер + інфузії~~ → надаються з 2 рівня через левелап (`levelup.ts:1357-1392`),
  недосяжно з `createCharacter` → [KR2.3](kr2.3-golden-levelup.md).
- **Новий пункт із розвідки:** transaction-блок character.ts:1143-1247 (природна броня за
  расою — Tortle, Monk/Barbarian unarmored defense) обгорнутий у `try/catch`, який **мовчки
  ковтає будь-яку помилку БД** (1245-1247). Побитий рядок сіда тут не завалить тест, а тихо
  дасть персонажа без броні. Матриця мусить явно покрити Tortle + Monk-без-броні +
  Barbarian-без-броні, і golden-файл мусить зафіксувати фактичний AC, а не «тест пройшов».
- Найдовший можливий шлях у конструкторі — **уточнено 2026-08-13**: варіант і підраса разом
  неможливі, `fullCharacterSchema` явно забороняє це (`raceVariantId` і `subraceId` одночасно →
  помилка валідації, character.ts superRefine). Тому найдовший реальний шлях — раса з варіантом
  (не підрасою) + клас з підкласом-на-1-рівні і опцією класу + походження з рисою-з-вибором
  (`backgroundFeatId` + `backgroundFeatChoiceSelections`) + риса з вибором + експертиза + мови.

## Як обирати

Не намагатись покрити декартів добуток — це тисячі комбінацій. Мета — щоб **кожна гілка
`if`-а** в `createCharacter` виконалась хоч раз. Практичний спосіб: увімкнути покриття
(`vitest --coverage`) на `src/lib/actions/character.ts` і додавати білди, доки не перестануть
з'являтися нові рядки.

## Журнал

**2026-08-13.** Розвідка коду `character.ts` перед побудовою матриці. Головний висновок:
`createCharacter` — це виключно створення рівня 1, одного класу. Вісь «Мультиклас» і три з
чотирьох «особливих випадків» (мультикласові слоти, Four Elements, інфузії Артифайсера) фізично
недосяжні звідси — перенесено в KR2.3. Warforged AC-бонус — не гілка, а зашитий `0`. Натомість
знайдено реальний ризикований шлях, якого не було в початковому списку: try/catch, що мовчки
ковтає помилки БД у блоці природної броні (character.ts:1143-1247) — саме туди йде Tortle і
безброньовий захист Monk/Barbarian. `PersFormData.equipment` і `.nameSchema` — мертві поля, не
читаються в `character.ts`, у матрицю не включати. `Background` не має жодного власного механізму
вибору (ні поля в схемі, ні `backgroundChoiceSchema`) — бекграунд може дати лише фіксовану рису
(`backgroundFeatId`), і вибір живе всередині цієї риси, не бекграунда. Чекаю звіт по сідах, щоб
підтвердити, які саме фонові риси реально мають робочий вибір.

**2026-08-13, продовження.** Звіт по сідах прийшов — і одразу зловив розбіжність із живими
даними: агент-розвідник написав, що ChoiceOption-рядки Resilient/Skill Expert мають `effectKind:
"ASI"`, а пряма перевірка проти `spells_test` показала, що в Resilient (і в Prodigy, і в Skilled)
`effectKind`/`effectAbility`/`effectSkill` насправді `null` — код розпізнає їх через легасі-парсинг
`optionNameEng` (`extractSkillsFromChoiceOption`/`extractExpertisesFromChoiceOption`,
characterUtils.ts:112-143 і легасі-fallback у самому character.ts). Тільки в Skill Expert
`effectKind` дійсно заповнений. Висновок: перед тим, як писати фікстуру з конкретними
choiceOptionId, значення дешевше перевірити прямим запитом до тестової БД, ніж довіряти
статичному аналізу коду сідів — розбіжність між «що написано в seed-скрипті» і «що реально лежить
у прод-дампі» цілком можлива.

Побудовано 34 білди (`tests/fixtures/builds/`), усі проходять через `createCharacter` і дають
детермінований golden (`tests/golden/creation/*.json`, дві незалежні прогони — байт-у-байт
однаково). Покриття `character.ts` (`vitest --coverage`): **75% рядків / 63% гілок / 74%
функцій**. Що лишилось не покритим — здебільшого рядки-охоронці (`race not found`, `background not
found`, `class not found`, `subclass не належить класу`) і catch-блок «Database error»: це
поведінка на невалідному вводі/збої БД, а не гілка бізнес-логіки, і для неї доречніший легкий
unit-тест, не golden-фікстура. Свідомо не гнався за 100% — decreasing returns.

Побічний ефект розширення: `bun run test` почав падати нестабільно («User not found») після
додавання другого DB-тестового файлу — Vitest за замовчуванням ганяє файли тестів паралельно, і
два файли з `beforeEach(resetUserData)` (TRUNCATE ... RESTART IDENTITY) навперебій труncatять
одну й ту саму `spells_test`. Той самий клас проблеми, що й [Р8](../DECISIONS.md#р8) — просто
локально, а не CI-проти-локального. Виправлено: `fileParallelism: false` у `vitest.config.mts`.

Три реальні розбіжності знайдено й задокументовано в [KNOWN-BUGS.md](../KNOWN-BUGS.md) — усі
навколо однієї теми: **сервер приймає id вибору без перевірки, що цей вибір узагалі доступний на
поточному рівні/для цього бекграунда.** Не виправлено, лише зафіксовано golden-файлами
(`druid-early-subclass-BUG`, `fighter-optional-feature-early-BUG`,
`background-feat-mismatch-BUG`).
