# Переїзд на Hetzner

**Статус:** ☐ план, нічого не розпочато · **Обсяг:** тільки `char.holota.family`
· **Спосіб:** Docker + compose

Сусідні сайти (`trgou.online`, `rgou.online`) і чужий кластер PG11 з `ur_db_prod` лишаються на
старому VPS. Поточний стан машини — [SERVER.md](SERVER.md).

## Головна небезпека, і як вона знімається

Під час зміни DNS обидва сервери деякий час отримують трафік. Якщо кожен пише у **свою** копію
бази, персонажі, створені на одному, не існують на іншому. Це не «трохи розсинхрон» — це втрата
даних реальних людей, і жоден бекап її не полагодить, бо обидві копії «правильні».

Знімається не обережністю, а порядком дій: **застосунок переїжджає першим, база — другою.** Поки
DNS перемикається, обидва сервери працюють з **однією і тією ж** старою базою. Split-brain стає
неможливим за побудовою.

Це працює тому, що порт 5454 уже доступний ззовні (перевірено: раннери GitHub у нього ходять).

## Що вже виміряно

| Факт | Значення | Чому важливо |
|---|---|---|
| TTL A-запису | ~300 с | вікно, коли живі обидва сервери, — 5 хвилин |
| DNS | Namecheap (`registrar-servers.com`) | там і міняється A-запис |
| CDN | немає | нічого не кешує, перемикання миттєве |
| Поточний IP | `31.131.17.213` | адреса для відкату |
| База | PG 16, `spells`, порт 5454 | на новій машині теж PG 16 |
| Розмір дампа | 3,6 MiB, знімається 6 с | перенесення бази — секунди, не години |

## Чесно про «zero downtime»

Для **застосунку** — так, досяжно: обидва сервери живі, база спільна, користувач нічого не помічає.

Для **бази** — ні. Момент, коли треба зупинити записи в стару й почати в нову, існує завжди.
Реалістично це **10-60 секунд** залежно від способу:

- логічна реплікація + рестарт контейнера — ~10 с;
- дамп/відновлення із заморозкою записів — ~60 с.

Хто обіцяє справжній нуль на однонодовій розкладці без pgbouncer — недоговорює. Пропоную визнати
це вікно, зробити його вночі й не будувати заради нього окрему інфраструктуру.

## Фаза 0 — Підготовка. Ризику нуль, прода не чіпаємо

- [ ] **Бекап на місці й перевірений.** Гейт, а не побажання: переїзд без відновлюваного бекапу —
      це азартна гра. [`scripts/db-backup.sh`](../scripts/db-backup.sh) написаний і відновлення
      перевірене, лишилось покласти на сервер і в cron.
- [ ] **Закрити відкриті питання з [SERVER.md](SERVER.md)** — повний юніт (`ExecStart`), звідки
      береться `DATABASE_URL`, чи обмежений 5454. **Не можна переїхати з машини, яку не вмієш
      описати.**
- [ ] **Розвідка Hetzner** — там уже щось крутиться, тож спершу той самий огляд, що робили для VPS:

```bash
free -m; df -h; nproc; uname -a
systemctl list-units --type=service --state=running --no-pager
ps aux --sort=-rss | head -15
docker --version; docker ps
sudo ss -ltnp
```

- [ ] **Знизити TTL до 60 с** у Namecheap за добу до переїзду. Копійчана дія, звужує вікно вп'ятеро.

## Фаза 1 — Контейнер. Локально, до всякого переїзду

Тут основна робота. На день переїзду її лишати не можна.

- [ ] `Dockerfile`: Next standalone + **Chromium для PDF із зафіксованою версією**
- [ ] `compose.yml`: застосунок, `restart: unless-stopped`, змінні оточення
- [ ] Postgres **не** контейнеризуємо — лишається на хості
- [ ] зібрати й підняти локально проти `spells_test`, **не проти прода**
- [ ] перевірити: `/`, `/spells`, `/magic-items` → 200
- [ ] **перевірити експорт PDF** — найризикованіше місце, і саме заради нього все це робиться
- [ ] перевірити, що застосунок читає `DATABASE_URL` там, де очікуємо

Поточна машина ганяє PDF через `@sparticuz/chromium` (`PUPPETEER_USE_SPARTICUZ=1`). У контейнері
розумніше системний `chromium` із `PUPPETEER_EXECUTABLE_PATH` — саме те, що README називає
найстабільнішим і що досі не було відтворюваним. Перевірити обидва варіанти локально.

## Фаза 2 — Hetzner паралельно. Трафіку ще немає

- [ ] поставити Docker, викотити контейнер
- [ ] **`DATABASE_URL` вказує на СТАРУ базу** (5454 на `31.131.17.213`) — це і є захист від split-brain
- [ ] **скопіювати `/etc/letsencrypt/` зі старого VPS**

Про сертифікати окремо, бо це класична пастка: certbot з HTTP-01 вимагає, щоб домен уже вказував
на сервер, а домен вкаже туди лише після перемикання — замкнене коло. Сертифікати це звичайні
файли й переносяться копіюванням. Тоді Hetzner віддає валідний TLS для `char.holota.family` **ще
до** зміни DNS. Після переїзду certbot на новій машині підхоплює поновлення.

- [ ] **перевірити все через `hosts` на своєму ноуті**, не чіпаючи DNS:

```
<IP_HETZNER>  char.holota.family
```

Цей прийом дає повноцінну перевірку з **справжнім доменом**: працює TLS, працює Google OAuth
(редірект іде на той самий домен), працюють усі маршрути. Тимчасовий піддомен так не вміє — під
нього довелося б окремо правити OAuth.

- [ ] `./scripts/smoke.sh https://char.holota.family` з підміненим `hosts` → 3 з 3
- [ ] вручну: логін, створення персонажа, **експорт PDF**
- [ ] переконатися, що створений так персонаж видно на **старому** сервері — це доказ, що база спільна

## Фаза 3 — Перемикання DNS. Застосунок переїхав, база ще стара

- [ ] A-запис у Namecheap → IP Hetzner
- [ ] ~5 хвилин обидва сервери живі, обидва пишуть **в одну базу** — розсинхрону не буде
- [ ] дивитись `tail -f /var/log/nginx/access.log` на старому, поки не затихне
- [ ] смоук проти реального домену

**Відкат:** повернути A-запис на `31.131.17.213`. П'ять хвилин, нічого не втрачено — база ж та сама.
Це найдешевша точка відкату в усьому плані.

## Фаза 4 — Переїзд бази. Єдине справжнє вікно

Увесь трафік уже на Hetzner, застосунок ходить у стару базу через мережу.

- [ ] поставити PG 16 на Hetzner, створити `spells`
- [ ] обрати спосіб:
  - **логічна реплікація** — `PUBLICATION` на старій, `SUBSCRIPTION` на новій, дочекатися нульового
    лагу, потім перемкнути `DATABASE_URL` і рестартнути контейнер (~10 с)
  - **дамп/відновлення** — зупинити застосунок, `db-backup.sh`, відновити, підняти (~60 с)
- [ ] звірити **точними `count(*)`**, не оцінками: `pers`, `pers_spell`, `pers_feature`, `pers_skill`,
      `account`, `user` — так само, як робили при перевірці бекапу
- [ ] `DATABASE_URL` → `localhost:5454`, рестарт
- [ ] смоук

**Це точка неповернення.** Після неї відкат на старий сервер означає втрату всього, що користувачі
створили на новій базі. Стару базу не чіпати щонайменше тиждень.

## Порядок, який я б тримав

Фаза 0 і Фаза 1 — не поспішаючи, вони не мають дедлайну і не чіпають прод. Фази 2-4 — одним
вечором, коли трафік найменший.

Найризикованіше — не DNS і не база, а **PDF**: єдине, що ламається від зміни оточення і чого не
видно, поки хтось не натисне «експорт». Тому він перевіряється двічі — у Фазі 1 локально і у
Фазі 2 через `hosts`.
