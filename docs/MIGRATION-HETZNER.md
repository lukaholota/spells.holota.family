## Головна небезпека, і як вона знімається

Під час зміни DNS обидва сервери деякий час отримують трафік. Якщо кожен пише у **свою** копію
бази, персонажі, створені на одному, не існують на іншому. Це не «трохи розсинхрон» — це втрата
даних реальних людей, і жоден бекап її не полагодить, бо обидві копії «правильні».

Знімається не обережністю, а порядком дій: **застосунок переїжджає першим, база — другою.** Поки
DNS перемикається, обидва сервери працюють з **однією і тією ж** старою базою. Split-brain стає
неможливим за побудовою.

Це працює тому, що порт 5454 уже доступний ззовні (перевірено: раннери GitHub у нього ходять).

Це знімає найнеприємнішу пастку плану: certbot із HTTP-01 вимагає, щоб домен уже вказував на
сервер, а він вказує на старий VPS. Сертифікат уже виписаний, тож копіювати `/etc/letsencrypt`

DNS вказує на старий VPS, HTTP-01 не пройде і поновлення впаде. Жорстка межа — 2026-09-26, коли
сертифікат стане недійсним. Переїзд варто зробити до кінця серпня.

## Чесно про «zero downtime»

Для **застосунку** — так, досяжно: обидва сервери живі, база спільна, користувач нічого не помічає.

Для **бази** — ні. Момент, коли треба зупинити записи в стару й почати в нову, існує завжди.
Реалістично це **10-60 секунд** залежно від способу:

- логічна реплікація + рестарт контейнера — ~10 с;
- дамп/відновлення із заморозкою записів — ~60 с.

Хто обіцяє справжній нуль на однонодовій розкладці без pgbouncer — недоговорює. Пропоную визнати
це вікно, зробити його вночі й не будувати заради нього окрему інфраструктуру.

Три речі, які з'ясувалися лише збіркою:

- **`next build` потребує живої бази** — `/char` пререндериться і читає `race.findMany()`.
  Тому `DATABASE_URL` подається BuildKit-секретом (`--mount=type=secret`), а не `ENV`, і в шарах
  образу не осідає. Збирати можна проти `spells_test` — контент той самий, у прод ходити не треба.
- **`prisma.config.ts` кидає помилку без `DATABASE_URL`**, хоча `generate` нікуди не підключається.
  `.env` у образ не потрапляє, тож у збірці стоїть завідомо непрацездатна заглушка.
- **`docker run --env-file` не знімає лапки**, на відміну від `source`. Це прямо конфліктує з
  правилом проєкту «значення в `.env` завжди в подвійних лапках» (воно існує, бо інакше `source`
  у `scripts/lib/pg.sh` ламається на `&`). Файл для Docker має бути **без** лапок, інакше значення
  приїжджає разом із ними й Prisma їде в неіснуючий хост.

Поточна машина ганяє PDF через `@sparticuz/chromium` (`PUPPETEER_USE_SPARTICUZ=1`). У контейнері
розумніше системний `chromium` із `PUPPETEER_EXECUTABLE_PATH` — саме те, що README називає
найстабільнішим і що досі не було відтворюваним. Перевірити обидва варіанти локально.

**Образ треба збирати під x86_64, а не на маку.** Hetzner — `x86_64`, машина власника — ARM.
Зібраний локально образ там не запуститься. Локальна збірка лишається способом **перевірити**
Dockerfile, а для деплою образ збирається там, де архітектура правильна: на раннері GitHub
(вони x86_64) з пушем у GHCR, або безпосередньо на сервері. Це рішення ще не ухвалене —
див. «Відкриті питання».

## Фаза 2 — Hetzner паралельно. Трафіку ще немає

Docker на машині вже стоїть (29.4.0), nginx-конфіг і сертифікат теж — див. «Що вже зроблено до нас».
Образ у реєстрі з 2026-08-09: `ghcr.io/lukaholota/char:latest` плюс тег за SHA коміта.

```bash
# 1. Логін у GHCR. Пакет приватний, тож потрібен PAT зі скоупом read:packages.
echo "$GHCR_TOKEN" | docker login ghcr.io -u lukaholota --password-stdin

# 2. Забрати образ (не збирати — збірка живе в CI, див. Відкриті питання №1)
docker pull ghcr.io/lukaholota/char:latest

# 3. Підняти. DATABASE_URL поки вказує на СТАРУ базу — це і є захист від split-brain.
docker run -d --name char --restart unless-stopped \
  --env-file /home/luka/char.env --shm-size=1g -p 127.0.0.1:3000:3000 \
  ghcr.io/lukaholota/char:latest
```

**З env-файлу для контейнера обов'язково прибрати `PUPPETEER_USE_SPARTICUZ`.** Це не косметика:
з ним PDF падає з 500. Next при збірці standalone **не тягне** бінарник `@sparticuz/chromium`
(тому старий `deploy.yml` і копіює `node_modules/@sparticuz/chromium/bin` окремим рядком), а в
образі його немає взагалі — перевірено `ls`. У контейнері натомість стоїть системний Chromium 151
і `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium` у самому Dockerfile.

**`--shm-size=1g` теж не косметика.** Chromium рендерить у `/dev/shm`; у Docker це **64 MB** за
замовчуванням проти **2 GB** на старому VPS. Прод має `PUPPETEER_DISABLE_DEV_SHM_USAGE=0`, тобто
`--disable-dev-shm-usage` не передається — отже браузер справді туди пише і на великих аркушах
упреться. Дрібний PDF пройде і без цього, тому дірку легко не помітити.

- [x] викотити контейнер, слухає `127.0.0.1:3000` — саме туди вже дивиться наявний `proxy_pass`
- [x] **зібрати env-файл із фактично діючих значень**, а не з файлів. На старому VPS їх два
      (`.env` і `.env.local`), другий мовчки перекриває перший, тож прочитати конфігурацію з файлів
      неможливо. Джерело істини — `/proc/<pid>/environ` живого процесу; звідти й беремо. Список
      змінних — у [SERVER.md](SERVER.md). У файлі для Docker значення **без лапок**.
- [x] **не забути `AUTH_TRUST_HOST` і `NEXTAUTH_URL`** — next-auth за проксі без них ламається.
      У локальній перевірці образу їх не було, тобто **логін у контейнері ще жодного разу не
      перевірявся**. Перевірити через `hosts` до перемикання DNS
- [x] **`AUTH_SECRET` перенести байт у байт.** Будь-яка зміна цього значення розлогінює всіх
      користувачів одночасно. Якщо в ньому виявиться хвіст `# Added by npx auth…` (перевіряється
      командою нижче) — переносити **разом із хвостом**, а чистити окремо й свідомо, не заодно
      з переїздом:

```bash
sudo tr '\0' '\n' < /proc/$(systemctl show char -p MainPID --value)/environ \
  | awk -F= '/^AUTH_SECRET=/ {v=substr($0,13); print "довжина:", length(v), "| містить решітку:", (v ~ /#/)}'
```
- [x] **`DATABASE_URL` вказує на СТАРУ базу** (5454 на `31.131.17.213`) — це і є захист від split-brain
- [x] перевірити, що чинний сертифікат справді віддається (`curl -vI` через `hosts`)

- [x] **перевірити все через `hosts` на своєму ноуті**, не чіпаючи DNS:

```

```

Цей прийом дає повноцінну перевірку з **справжнім доменом**: працює TLS, працює Google OAuth
(редірект іде на той самий домен), працюють усі маршрути. Тимчасовий піддомен так не вміє — під
нього довелося б окремо правити OAuth.

- [x] `./scripts/smoke.sh https://char.holota.family` з підміненим `hosts` → 4 з 4
- [x] вручну: логін, створення персонажа, **експорт PDF**
- [x] переконатися, що створений так персонаж видно на **старому** сервері — це доказ, що база спільна

**Хвіст, який тут не зловили** (знайдено вже після Фази 4, див. Журнал): у контейнерній збірці

### Закриття Postgres від інтернету — покроково

**Складна половина цього пункту зникла 2026-08-10.** Увесь порядок «спершу gitea, потім
`listen_addresses`» існував заради чужих баз. Адам, чиї вони, сказав, що їх **можна просто
покласти**. Тобто зникла і залежність від `/home/adam/`, яку ми все одно не читаємо, і
найкрихкіше місце задуму — прив'язка до шлюзу `172.20.0.1`, що міг переїхати після
`docker compose down`.

Лишається одна зміна в одному файлі. Наші споживачі перевірені — усі внутрішні:

| Хто | Адреса |
|---|---|
| контейнер `char` | `172.17.0.1:5432` |
| бекапи в cron | `127.0.0.1:5432` |
| CI і локальна розробка | SSH-тунель → `127.0.0.1` |

**0. Знімок споживачів — щоб знати, що саме зламається.** Без sudo `client_addr` чужих сесій не
видно взагалі, тому крок обовʼязково від `postgres`:

```bash
sudo -u postgres psql -Atc "select coalesce(datname,'-'), coalesce(usename,'-'), \
  coalesce(host(client_addr)::text,'local'), count(*) \
  from pg_stat_activity group by 1,2,3 order by 1,3"
```

Це вже не гейт, а запис у журнал: якщо там виявиться хтось, крім `spells`, `giteadb` і `fence`,
варто спитати Адама ще раз, перш ніж продовжувати.

**1. Звузити `listen_addresses` і перезапустити кластер.** У
`/etc/postgresql/17/main/postgresql.conf`:

```
listen_addresses = 'localhost,172.17.0.1'
```

```bash
sudo systemctl restart postgresql@17-main
```

Саме рестарт — `listen_addresses` reload не підхоплює. Це єдиний момент із простоєм: усі
підключення рвуться на секунду-дві, Prisma підніме пул заново. Робити при малому трафіку.

Якщо адреси не існує (бриджа докера немає), Postgres пише WARNING і піднімається далі, а падає
лише коли не зміг зайняти **жодної** — `localhost` тримає цю гарантію. Перевірити в логу після
першого рестарту, а не вірити на слово.

**2. Перевірити ззовні, а не по `ufw`.** На старому VPS `ufw status` показував порт закритим,
поки він приймав зʼєднання з інтернету — тому єдина чесна перевірка робиться з чужої машини:

```bash
nc -z -w 5 157.90.114.54 5432; echo $?    # має бути НЕ 0; 2026-08-10 до закриття було 0
```

Плюс зсередини: `curl -s https://char.holota.family/api/health` → `database:true`,
`./scripts/db-backup.sh` відпрацьовує, `bun run test` через тунель зелений.

**Що зламається свідомо:** gitea втратить базу. Її контейнер піднятий із `restart: always`, тож
він, найімовірніше, піде в цикл перезапусків і смітитиме в логи. Гасити чужий контейнер — не наша
дія; про це варто сказати Адаму. База `fence` — так само.

**Відкат:** повернути `listen_addresses = '*'` і перезапустити кластер.

**Якщо gitea колись знадобиться назад** (розвідка вже зроблена, шкода викидати): вона живе в
мережі `gitea_gitea`, підмережа `172.20.0.0/16`, шлюз **`172.20.0.1`** — не `172.17.0.1`, який
належить стандартному бриджу з нашим контейнером. Треба: додати цю адресу в `listen_addresses`,
дозволити `host giteadb gitea 172.20.0.0/16 scram-sha-256` у `pg_hba.conf`, поставити
`GITEA__database__HOST=172.20.0.1:5432` у `/home/adam/gitea/docker-compose.yml`, прибити там же
підмережу мережі (інакше `docker compose down` її переїде) і піднімати саме
`docker compose up -d`, бо `docker start` нових змінних не читає.

## Журнал

**2026-08-09 — розвідка Hetzner, три несподіванки.**

- **Найбільша: там уже є робочий nginx-конфіг для `char.holota.family` і чинний сертифікат.**
  Залишок ранішої спроби переїзду. Конфіг проксює саме на `127.0.0.1:3000`, тобто рівно туди, куди
  слухатиме наш контейнер. План від цього спрощується — крок «скопіювати `/etc/letsencrypt` зі
  старого VPS» видалено за непотрібністю. Натомість з'явився дедлайн: поновлення сертифіката
  впаде ~27 серпня, поки DNS вказує на старий сервер.
- **Postgres там 17, а не 16.** Сам перенос це не ламає (дамп з 16 у 17 відновлюється), але
  створювати базу треба з явною локаллю: Debian 13 + PG17 схиляються до ICU, а джерело на libc
  `en_US.utf8`. Мовчазний дефолт змінив би порядок сортування українського тексту.
- **Свопу нема взагалі**, при тому що на машині вже живуть azuracast, gitea і PG17. З Chromium
  для PDF це прямий шлях до OOM. Додано у Фазу 0.

Виміряно на проді для переносу бази: розширень немає жодного, крім `plpgsql`; локаль
`en_US.utf8`; роль з логіном одна — `postgres`, і застосунок ходить під нею, тобто суперюзером.
Звузити права варто, але **не під час переїзду** — одна зміна за раз.

**2026-08-09 — Фаза 2 піднята, і одразу зловила поломку PDF.** Образ забрано на Hetzner (digest
збігся з тим, що запушив CI), контейнер стартував. Перевірено звідси через
`curl --resolve char.holota.family:443:157.90.114.54`, тобто зі справжнім доменом і TLS, але без
жодних змін у DNS:

| Що | Результат |
|---|---|
| `/api/health` з Hetzner | **200**, `{"status":"ok","database":true}` |
| `/`, `/spells`, `/magic-items` | 200 |
| Сертифікат | `CN=char.holota.family`, Let's Encrypt, `verify ok`, до 26.09 |
| **Експорт PDF** | **500** |

Тобто головна конструкція фази підтверджена — новий застосунок ходить у **стару** базу, — а PDF
зламався рівно так, як і передбачалось у [Р9](DECISIONS.md#р9): це єдине, що ламається від зміни
оточення і чого не видно, поки хтось не натисне «експорт».

**Причина знайдена відтворенням, не здогадкою.** Той самий образ локально: без прапорця PDF
віддає 200, з `PUPPETEER_USE_SPARTICUZ=1` — 500 зі стектрейсом у
`@sparticuz/chromium/build/esm/index.js:124`. `ls` в образі підтверджує: теки
`node_modules/@sparticuz/chromium/bin` там немає — Next її в standalone не тягне. Прапорець
приїхав із прод-оточення, скопійованого як є.

**Заодно знайдено другу міну, яка ще не вистрілила:** `/dev/shm` у контейнері **64 MB** проти
**2 GB** на старому VPS, а `PUPPETEER_DISABLE_DEV_SHM_USAGE=0` означає, що Chromium туди таки
пише. Дрібний PDF проходить, великий аркуш упреться. Лікується `--shm-size=1g` (додано і в
`compose.yml`). Це саме той випадок, коли перевірка на маленькому прикладі дає хибну впевненість.

**2026-08-09 — PDF на Hetzner полагоджено, Фаза 2 закрита в частині, яку можна перевірити з
терміналу.** Після прибирання `PUPPETEER_USE_SPARTICUZ` з env-файлу і `--shm-size=1g`:

| Що | Hetzner | Локально |
|---|---|---|
| `/api/health` | 200, `{"status":"ok","database":true}` | 200 |

| Шрифти | `NotoSans-Regular/Bold`, `LiberationSerif-Bold` | ті самі |

Розмір збігся **байт у байт** із локальним прогоном — сильний сигнал, що образ на обох машинах
поводиться однаково, попри різні архітектури (ARM локально, x86_64 на сервері).

**Мораль про перевірки на дрібних прикладах.** `--shm-size` знайдено не падінням, а порівнянням
`/dev/shm`: 64 MB у контейнері проти 2 GB на старому VPS. Трьохзаклинальний PDF пройшов би і без
нього — тобто перевірка на маленькому прикладі дала б хибну впевненість, і воно вистрілило б на
першому великому аркуші вже після переїзду.

**2026-08-09 — логін на Hetzner перевірено, Фаза 2 закрита повністю.** Це було останнє, чого не
дістати з терміналу. Провайдерів виявилось два — звичайний `google` (редіректний потік) і

Побічно з'ясувалося, що припущення «Google Console не пустить, бо там дозволений лише
char.holota.family, а DNS веде на VPS» — хибне. Google звіряє **рядок** `redirect_uri`, а не те,
куди домен резолвиться. Перевірено порівнянням `/api/auth/providers` на обох машинах: відповіді
ідентичні символ у символ, тобто Google отримує однаковий `callbackUrl` і відрізнити сервери не

**2026-08-09 — Фаза 4. Вікно 14 секунд. Репетиція окупилася чотири рази.**

Головний висновок сесії: **репетиція знайшла чотири помилки, кожна з яких спрацювала б усередині
простою** — тобто в момент, коли розбиратися найдорожче. Жодну з них не було видно з тексту плану.

1. **`localhost` у рядку підключення.** План казав `DATABASE_URL → localhost:5432`. Але це рядок
   для контейнера, а `localhost` усередині контейнера — сам контейнер. Треба `172.17.0.1`.
2. **Порт.** В одному місці плану стояв ще й `5454` — порт старої машини.
3. **`pg_hba.conf` відхиляє суперюзера по мережі.** Рядок `host all postgres 0.0.0.0/0 reject`
   поставлений свідомо; пускає лише `127.0.0.1`. Плану цього не знав узагалі. Контейнер приходить
   з `172.17.0.x`, тобто «по мережі», і був би відкинутий.
4. **`docker start` не підхоплює змінений `--env-file`.** Він читається лише при створенні
   контейнера. Застосунок мовчки піднявся б зі старим рядком підключення — найгірший варіант,
   бо виглядав би здоровим.

**Звідси рішення завести окрему роль `char_app`** замість переносу суперюзера — див.
[Р10](DECISIONS.md#р10). Перевірено до вікна: відновлення під нею проходить, 65 з 65 таблиць і
51 з 51 послідовності доступні, `UPDATE` і `nextval` працюють.

**Як пройшло вікно.** `docker stop` → дамп 9 с (3,7 MiB, 602 об'єкти) → `pg_restore` 1 с → звірка
→ новий env → перестворення контейнера. **14 секунд**, `/api/health` 200. Смоук 4 з 4, PDF 200 і
`application/pdf`, кирилиця на місці (`є`, `і`, `U+FFFD` немає), і під час генерації PDF прочитав
15 рядків уже з нової бази — тобто ланцюг перевірено наскрізь, а не за здоровим глуздом.

Скрипт вікна писався з **автоматичним відкатом**: будь-яка розбіжність у звірці або нездоровий

**2026-08-09 — знайдено регресію, якої переїзд не спричинив, але й не показав: Google One Tap.**

Полагоджено: `ARG`/`ENV` у `Dockerfile` плюс `build-args` в `image.yml`. Додано запобіжник, який
**валить збірку** на порожньому значенні — перевірено окремою збіркою, що без змінної він дає
`exit 1`, а зі змінною проходить. `NEXT_PUBLIC_SITE_URL` тим самим не зачеплений: у всіх шести
місцях є запасне значення.

**Заодно знешкоджено міну в `deploy.yml`.** Він на кожен пуш у `main` збирав і робив
`systemctl restart char` **на старому VPS**, а смоук ганяв по `char.holota.family`, тобто вже по
Hetzner. Тобто пуш воскресив би другий застосунок над застарілою базою — і показав би зелений
смоук, бо перевіряв би не той сервер. Джоба викочування переведена на ручний запуск;

**2026-08-09 — початок Фази 5: бекапи, тестові бази, два баги в `db-clone.sh`.**

Скрипти проєкту покладені на Hetzner у `/home/luka/char-ops/` — репозиторію там немає, застосунок
живе в контейнері. `.env` там **у лапках**, на відміну від env-файлу для Docker: цей читається
через `source`.

**Перший баг: голий `CREATE DATABASE`.** Без явної локалі копія успадковує дефолт кластера, а він
тут `C.utf8` — тобто тести працювали б на базі, яка сортує українські назви інакше, ніж прод.
Перевірено контрольним створенням: `probe_scratch` вийшла саме `C.utf8`. Полагоджено — локаль,
кодування і власник читаються **з бази-джерела**, а не з дефолтів кластера.

**Другий баг знайшовся тільки тим, що тести реально запустили.** `pg_restore --no-owner` робить
власником об'єктів того, хто підключився, а підключитись мусить роль із `CREATEDB`, тобто
суперюзер. Виходила база, що належить `char_app`, і таблиці, що належать `postgres`: тести падали
на `TRUNCATE` з `permission denied for table _ChoiceOptionToPers`. Перша спроба полагодити через
`REASSIGN OWNED BY postgres` теж провалилась — Postgres не віддає об'єкти бутстрап-суперюзера.
Працює лише поштучна зміна власника: таблиці, послідовності, в'юхи, enum-и.

Мораль обох: клон, який «начебто створився», не доводить нічого. Довели два прогони — `65 з 65
таблиць доступні char_app` і `bun run test` 33/33 з кодом виходу 0.

**Окремо про код виходу, бо на цьому вже спіткнулись.** У zsh `PIPESTATUS` порожній — масив
зветься `pipestatus`. Тому `cmd | tail; rc=${PIPESTATUS[0]}` мовчки дає порожнє значення замість
коду, і перший прогін тестів був прочитаний неправильно. Правильно — писати вивід у файл і брати
`$?` без конвеєра.

**2026-08-10 — R2 і CI. Старий VPS більше не потрібен ні для чого, крім страховки.**

**R2.** Бакет `char`, префікс `db_dumps`, rclone поставлений у `~/bin` розпакуванням архіву
(`unzip` на машині немає, розпаковували python-ом), тож sudo не знадобився. Вивантаження йде тим
самим cron одразу після дампа.

Два свідомі рішення в `backup-to-r2.sh`:

- **`copy`, а не `sync`.** Sync повторив би локальне видалення в хмарі — тобто втрата диска або
  шифрувальник забрали б із собою й резервну копію. Саме те, від чого копія й потрібна.
- **Погодинні в хмарі живуть 3 дні, добові й місячні — вічно.** 24 дампи на добу це ~89 МБ; за
  місяць вийшло б за безкоштовний ліміт R2 у 10 ГБ.

**Обіцянку з Фази 0 довелося виправити.** Там записано «токен тільки на запис, без права
видалення». **R2 такого пресета не має** — `Object Read & Write` включає `DeleteObject`, а
пресетів між ним і read-only немає. Тобто зламаний сервер зможе стерти й хмарну копію. Прийнято

**CI.** Тунель винесений у складену дію, а не скопійований у два воркфлоу — копії тут розходяться,

**Пастка, яку впіймали до прогону:** кроки `RUN` усередині `docker build` живуть у власній мережі,
тож `127.0.0.1:5454` там вказував би на build-контейнер, а не на тунель, піднятий на раннері. Це
буквально та сама помилка, що з `localhost` у рядку підключення контейнера, тільки на рівні
збірки. Лікується `network=host` у buildx **і** в `build-push-action` — обидва місця.

**І ще одна:** `ssh -f` повертає нуль, щойно пішов у фон, а не коли порт почав відповідати. Без
явної перевірки порту джоба падала б пізніше й з іншим текстом — на Prisma.

**Дві перевірки, які були непереконливі, і як полагоджено.** Перший пробний cron читав лог, щойно
в ньому з'явився перший рядок, — тобто до того, як відпрацював крок вивантаження, і нічого про
нього не доводив. Замінено на запуск усього ланцюга через `env -i` з cron-івським `PATH`: це
відповідає на справжнє питання «чи знайдеться rclone», і дало `rc=0`.

**2026-08-10 — деплой, shadow-база, розвідка перед закриттям Postgres.**

**Деплой знову існує.** `deploy.yml` переписаний на «забрати образ із GHCR», `image.yml`
прибраний: тепер один воркфлоу `checks → image → deploy`. Послідовність замість паралельності
свідома — образ, який не пройшов тести, не має потрапляти в GHCR. Раніше це нічого не коштувало,
бо образ нікуди й не їхав; тепер коштувало б продом.

Викочування синьо-зелене: новий контейнер піднімається на **вільному слоті** (3000 ↔ 3002, бо
3001 зайнятий gitea), перевіряється по `/api/health` ще до трафіку, і лише тоді перемикається
`upstream` у nginx. Старий контейнер лишається живим до зеленого смоуку — саме це робить відкат
миттєвим, і саме цього не дає `docker rm -f`, після якого відкочуватись нема на що. Симлінк
`current` замінився на `/etc/nginx/conf.d/char-upstream.conf`, а `previous-release` — на
`/home/luka/char-ops/previous-port`; логіка відкату з [KR1.5](o1-safety-net/kr1.5-smoke-before-deploy.md)
збережена рядок у рядок.

**Прогін гілок відмови знайшов два тихі баги — обидва в класі «мовчки зробив не те».** Це і є
причина, з якої гілки треба ганяти, а не читати:

1. **`retire` при зниклому конфізі nginx гасив контейнер і повертав нуль.** Перевірка стояла як
   `[ "$previous" != "$(find_active_port)" ] || …`, а всередині `||`-списку `set -e` вимкнений:
   невдалий `find_active_port` віддавав порожній рядок, який «не збігається» з чим завгодно, і
   перевірка пропускала. Полагоджено окремим присвоєнням; після правки — `rc=1` і відмова.
2. **Невідомий активний порт мовчки давав слот 3000.** `find_standby_port` повертала перший порт,
   що не дорівнює активному, тож для активного `9999` вона віддавала `3000` — тобто деплой поліз
   би саме в той контейнер, який тримає трафік. Тепер спершу перевіряється, що активний порт
   узагалі зі списку слотів: `9999` → відмова, `3000` → `3002`, `3002` → `3000`.

**І третій, найгірший — знайдений питанням «а що там перевіряти на тому nginx».** Якщо разова
підготовка не влучить у рядок `proxy_pass` і в сайті лишиться прибитий `127.0.0.1:3000`, то
підміна upstream не робить **нічого**, смоук зелений — бо його обслуговує **старий** контейнер, —
а `retire` гасить саме той контейнер, який віддає трафік. Сайт лягає вже після зеленого деплою,
тобто автовідкат не спрацює за побудовою.

Спершу це було записане в SERVER.md як «перевір очима». Замінено на перевірку в самому
`deploy-container.sh` (`require_site_uses_upstream`), яка робиться до будь-якої дії. Перевірено на
червоному: проти справжнього конфіга сайту, який зараз **не** підготовлений, `release` дає `rc=1`
і пояснення; проти конфіга, пропущеного через `sed` із рунбука, — проходить далі й падає вже на
неіснуючому тезі образу. Побічно це довело, що `sed` із SERVER.md справді влучає в реальний файл.

**Що ще перевірено.** Найризикованіше припущення — що на машині взагалі можна тримати два
контейнери одночасно: другий піднято на 3002 з тим самим `char.env`, він
відповів `{"status":"ok","database":true}` на другій спробі (≈5 с). Виміряно й ціну перекриття:
живий 22 години контейнер тримає **1,18 GiB**, щойно піднятий — **162 MiB**. Тобто вікно деплою
коштує ~200 MB, а не другу копію 1,2 GiB: у довгожителя це переважно накопичена куча Node.
**Не перевірено:** сам деплой не виконувався жодного разу — він потребує разової підготовки
сервера від root ([SERVER.md](SERVER.md#разова-підготовка-під-деплой)). Гілка відкату, як і
раніше з KR1.5, не виконувалась ніколи.

**Ціна, яку платимо за деплой без пароля sudo.** `SUDO_PASSWORD` у секретах датований 1 січня і
є паролем **старої** машини, тобто на Hetzner не працює; тягнути повний sudo-пароль у CI не
хотілось. Натомість `luka` отримує NOPASSWD рівно на `nginx -t` і `nginx -s reload`, а файл
upstream належить `luka`. Це означає, що ключ раннера може написати довільний конфіг у
`http`-блок nginx і змусити його перечитатись. Прийнято свідомо: `luka` і так має повний sudo по
паролю і креденшели до бази. Альтернатива «дати sudo на скрипт» гірша — скрипт лежить у теці,
яку `luka` пише.

**Shadow-база прибрана.** `prisma.config.ts` більше не передає `shadowDatabaseUrl`, змінної немає
ні в локальному `.env`, ні в `char.env` на сервері (у `.env.example` її не було ніколи).
`bunx prisma generate` після цього — код виходу 0, свіжий контейнер піднявся здоровим. Стара
копія лишилась у `char.env.bak-shadow`. Живий контейнер змінну ще має: `--env-file` читається
при створенні, тож вона зникне з першим же деплоєм.

**Розвідка перед закриттям Postgres дала одну справжню поправку до плану.** У плані стояло
«перевести gitea на `172.17.0.1`». Це шлюз стандартного бриджа, де живе **наш** контейнер, а
gitea в іншій мережі — `gitea_gitea`, підмережа `172.20.0.0/16`, шлюз **`172.20.0.1`**. Помилка
того ж роду, що й `localhost` у рядку підключення у Фазі 4: адреса «хоста» залежить від того, з
якої мережі дивитися. Плюс `/home/adam/gitea/docker-compose.yml` нам не читається — правку робить
власник.

Заміряно «до»: `nc -z 157.90.114.54 5432` з машини власника — **код 0**, тобто база справді
приймає зʼєднання з інтернету. Порт 3000 при цьому закритий (код 1), як і має бути.

**Того ж дня — перший справжній деплой новим механізмом, наскрізь зелений.** Прогін
[31425756592](https://github.com/lukaholota/char/actions/runs/31425756592). Момент вибраний за

| Джоба / крок | Час |
|---|---|
| `checks` | 49 с |
| `image` | 3 хв 55 с (проти 8 хв 19 с окремим воркфлоу — кеш) |

перевіряється. Далі upstream → 3002, `previous-port` → 3000, і лише після зеленого смоуку старий

Що закрилося цим прогоном: викочування по SSH під деплой-користувачем, `docker login` разовим

спрацював саме так, як задумано — по імені він би не знайшовся). Живий контейнер тепер прибитий

Тобто перезапуск застосунку віддає системі майже гігабайт, і це аргумент не тримати контейнер
місяцями.

**Що НЕ закрилося:** гілка відкату пропущена, бо смоук зелений. Як і записано в KR1.5, вона сама
собою не виконається ніколи.

**Три дрібниці, знайдені принагідно.** У кластері є чужа база `fence` з власною роллю — хто в неї
ходить, невідомо, і це треба зʼясувати **до** звуження `listen_addresses`. Сайт

## Фаза 4 — покроково

Стан на вході: трафік на Hetzner, застосунок у контейнері, база **ще на старому VPS**
(`31.131.17.213:5454`). Кожен запит до бази йде через інтернет — це видно на `/spells`,
2,16 с проти 1,79 с раніше.

**Перед вікном (простою немає):**

1. Переконатись, що на старому VPS трафіку немає: `sudo tail -f /var/log/nginx/access.log`.
2. **Зупинити старий застосунок:** `sudo systemctl stop char`. Це прибирає другого можливого
   писача в стару базу — інакше запізнілий резолвер міг би привести користувача туди вже після
   того, як ми зняли фінальний дамп, і цей запис зник би. Відкат — `systemctl start char`.
3. На Hetzner створити базу **з явною локаллю** (`LOCALE_PROVIDER libc`, `en_US.utf8`,
   `TEMPLATE template0`) — інакше PG17 на Debian 13 візьме ICU і зіпсує сортування української.
4. Задати пароль ролі, під якою підключатиметься застосунок. Зараз він ходить суперюзером
   `postgres`; звужувати права — **окремо, не під час переїзду**.
5. **З'ясувати, хто ще використовує PG17 на Hetzner** (ймовірно gitea), перш ніж чіпати
   `listen_addresses` чи `pg_hba.conf`.

**Вікно (сайт лежить ~1-2 хвилини):**

6. `docker stop char` — з цієї миті записів немає ні звідки.
7. Фінальний дамп зі старої бази: `./scripts/db-backup.sh` (6 с, 3,6 MiB).
8. Відновити в нову: `pg_restore --no-owner --no-privileges --dbname=... --jobs=4`.
9. **Звірити точними `count(*)`** по `pers`, `pers_spell`, `pers_feature`, `pers_skill`, `spell`,
   `class`, `race`, `background`, `account` — так само, як робили при перевірці бекапу. Не
   збіглося — не продовжувати.
10. `DATABASE_URL` у env-файлі → `char_app@172.17.0.1:5432/spells`. **Не `localhost`** — усередині
