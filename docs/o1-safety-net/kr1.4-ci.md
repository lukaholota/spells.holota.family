# KR1.4 — CI блокує зламаний деплой

**Ціль:** [O1](README.md) · **Статус:** 🔄 в роботі — воркфлоу написано й перевірено локально,
**чекає на дві дії власника** (див. кінець) · **Залежить від:** KR1.2 ✅, KR1.3 ✅

## Навіщо

Зараз `.github/workflows/deploy.yml` на push у `main` збирає й одразу викочує на VPS. Жодної
перевірки перед цим — ні типів, ні лінта, ні тестів. Тобто зламаний код їде в прод автоматично.

Тести з KR1.2/1.3 нічого не варті, поки їх не запускають без участі людини.

## Кроки

**1. ~~Спочатку перевірити, що `tsc --noEmit` взагалі проходить.~~** Перевірено 2026-08-08: rc=0
на чистому дереві, попри 656 `as any`. `bun run lint` теж rc=0 (366 warnings, 0 errors). Робити
обидва блокуючими можна одразу, тимчасово-неблокуючий варіант не знадобився.

**2. Джоба.** Реалізовано в [.github/workflows/deploy.yml](../../.github/workflows/deploy.yml).
Розходиться з початковим начерком у трьох місцях, і всі три варто розуміти:

- **немає `services: postgres`** — локальний Postgres у раннері дав би порожню базу без контенту,
  тобто рівно ту проблему, через яку взагалі виникло [Р8](../DECISIONS.md#р8). Замість нього
  `spells_ci_test` на сервері через `TEST_DATABASE_URL`;
- **немає `psql -f db/schema.sql` і `-f db/content.sql`** — база вже існує і вже з контентом;
  `db/content.sql` не створюється взагалі;
- **з'явився крок `generate:spells`, і він мусить стояти перед `tsc`.** Цього в начерку не було,
  і воно неочевидне — деталі в журналі.

Плюс `concurrency` на джобі (щоб два прогони не били по одній базі) і `if` на деплої (щоб він не
запускався на pull request, бо тригер тепер не лише push).

**3. Гілки.** Зараз усе комітиться прямо в `main`. Це не проблема сама по собі, поки `checks`
блокує деплой. Але якщо захочеться бачити результат **до** того, як воно поїде в прод — треба
перейти на PR-флоу. Це окреме рішення, тут не вирішуємо.

## Журнал

**2026-08-08 — `db/content.sql` із кроку 2 не існує, і без нього CI зелений не буде.** Виміряно в
[KR1.3](kr1.3-test-database.md), не припущено: на базі, піднятій з `db/schema.sql` на порожньому
кластері, `vitest run` дає rc=1 — `1 failed | 29 passed | 3 skipped`. Схема накочується ідеально
(65 таблиць, 35 enum, 103 FK, нуль помилок), але контенту немає, тож перевірка контенту падає, а
тести персонажа скіпаються на `beforeAll`, який не знаходить ні класу, ні раси, ні походження.

Варіанти, між якими треба вибрати **до** того, як писати yaml:

1. **Генерувати `db/content.sql`** у репозиторій (окремий скрипт поряд із `db-dump.sh`). Контентний
   дамп у custom-форматі важить ~857 KB, у текстовому буде більше. Плюс: CI повністю автономний.
   Мінус: великий генерований файл у git, який змінюється щоразу після правки контенту.
2. **Окрема база на сервері для CI** з обмеженими креденшелами в GitHub Secrets. Плюс: нічого не
   комітимо, дані завжди свіжі. Мінус: CI залежить від доступності VPS, а креденшели виїжджають
   за межі машини власника.
3. **Розділити тести** на чисті й ті, що потребують контенту, і ганяти в CI поки що тільки чисті
   (зараз це 29 з 33). Плюс: робиться одразу, нічого не коштує. Мінус: CI не ловить регресії в
   тому, заради чого все й затівалося.

Найімовірніше 3 як перший крок і 1 як ціль. Але це рішення власника, і його варто записати в
[DECISIONS.md](../DECISIONS.md), а не залишати в yaml.

**2026-08-08 — `tsc --noEmit` уже проходить.** Крок 1 плану («спочатку перевірити») можна не
робити наосліп: станом на цю дату `bunx tsc --noEmit` дає rc=0 на чистому дереві, попри 656
`as any`. `bun run lint` теж rc=0 — але 366 warnings, тож робити лінт блокуючим можна лише за
поточного налаштування «warnings не валять збірку». Одна помилка від нового коду вже ловилася
(`react-hooks/rules-of-hooks` на тестовому хелпері) — тобто eslint у цьому проєкті таки червоніє
по-справжньому, це не декорація.

**2026-08-08 — рішення ухвалено: окрема база для CI, дампу в git не буде.** Записано як
[Р8](../DECISIONS.md#р8). Аргумент «секрети не варто вивозити в GitHub» виявився слабким і знятий:
там уже лежать прод-`DATABASE_URL`, `SSH_PRIVATE_KEY` і `SUDO_PASSWORD`. Справжня причина, з якої
рішення взагалі потребувало обговорення, — інша: тести роблять `TRUNCATE`, і спільна з власником
`spells_test` давала б перегони. Тому окрема `spells_ci_test` плюс `concurrency` на джобі.

**2026-08-08 — сюрприз: `generate:spells` мусить іти перед `tsc`, інакше CI червоний на порожньому
місці.** `src/lib/spellsData.ts:8` імпортує `@/lib/generated/spells.json`, а цей файл у
`.gitignore` (`magicItems.json` поруч — навпаки, закомічений). Локально він є, тому `tsc` завжди
проходив. На чистому клоні його немає, і `tsc` падає:

```
src/lib/spellsData.ts(8,24): error TS2307: Cannot find module '@/lib/generated/spells.json'
```

Перевірено не міркуванням: файл тимчасово прибрано, `tsc` дав **rc=2** з цією помилкою, після
повернення — знову rc=0. Наслідок: крок генерації обов'язковий, і йому потрібен доступ до бази
(скрипт читає заклинання з Postgres). Тобто `checks` не може бути «просто tsc + lint» навіть
теоретично — без БД він не проходить взагалі.

**2026-08-08 — уся джоба прогнана насухо на клоні репозиторію.** Вгадувати по одному файлу, чого
ще не вистачає в чистому клоні (`next-env.d.ts` теж у `.gitignore`), — шлях до п'яти червоних
прогонів поспіль. Замість цього зроблено те, що робить сам GitHub: `git clone` у тимчасову теку і
повна послідовність кроків із `DATABASE_URL` **тільки** зі змінної оточення.

У клоні, як і очікувалося, немає ні `.env`, ні `.env.test`, ні `spells.json`, ні `next-env.d.ts`.
Результат:

| Крок | rc |
|---|---|
| `bun install --frozen-lockfile` | 0 |
| `bunx prisma generate` | 0 |
| `bun run generate:spells` | 0 |
| `bunx tsc --noEmit` | 0 |
| `bun run lint` | 0 |
| `bun run test` | 0 — 33/33 |

Тобто відсутність `next-env.d.ts` тестам і типам не заважає (типи Next приходять із пакета), а
`spells.json` закриває крок генерації. Окремо підтверджено, що `tests/setup.ts` бере
`DATABASE_URL` зі змінної оточення, коли `.env.test` немає — саме цей шлях і буде в CI.

**Чого ця симуляція НЕ доводить.** Раннер GitHub — не ця машина. Не перевірено й перевірити звідси
неможливо: чи дістають раннери порт 5454 на VPS (якщо на сервері є allowlist по IP, перший прогін
впаде на таймауті конекту), скільки насправді займе прогін через інтернет замість локальної мережі,
і чи не впреться щось у версію bun з `bun-version: latest`. Це з'ясується першим реальним прогоном.

**2026-08-08 — перший реальний прогін зелений, обидві невідомі закрилися.**
[PR #3](https://github.com/lukaholota/char/pull/3), джоба `checks` — 49 с.

| Що перевірялося | Результат |
|---|---|
| чи дістає раннер GitHub порт Postgres на VPS | **так** — `generate:spells` витягнув 501 заклинання з `spells_ci_test` |
| час усієї джоби | 49 с при бюджеті 5 хвилин |
| час тестів через інтернет | 4,22 с проти 1,7 с локально |
| чи не поїхав деплой на pull request | ні — `build-and-deploy` пропущено за 0 с, `if` спрацював |

**Прогноз про час був завищений.** У першій редакції [Р8](../DECISIONS.md#р8) написано, що
локальні 2 с у CI стануть «десятками секунд». Насправді затримка мережі подвоює час, а не
збільшує на порядок. Документ виправлено — щоб наступного разу оцінка спиралася на цифру, а не
на побоювання.

Перед PR прогнано тести локально безпосередньо проти `spells_ci_test` (501 заклинання, 13 класів,
66 рас, 90 походжень, 0 персонажів) — саме щоб перший прогін не впав на тому, що база порожня або
секрет веде не туди.

**Дрібниця на майбутнє:** GitHub лишає попередження, що `actions/checkout@v4` цілиться в Node 20,
який виведено з ужитку, і примусово запускає його на Node 24. На результат не впливає, але колись
варто підняти до `@v5` — в обох джобах.

**Що лишилось:** змержити PR. Саме на `main` уперше відпрацює зв'язка `checks` → `build-and-deploy`
— тобто те, заради чого KR і затівався. Це водночас перший деплой на прод із цієї гілки.
