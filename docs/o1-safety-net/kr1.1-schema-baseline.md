# KR1.1 — Схема як відтворюваний артефакт

**Ціль:** [O1](README.md) · **Статус:** ✅ зроблено 2026-08-07 · **Блокує:** KR1.3, KR5.2

## Навіщо

Зараз схему неможливо підняти з нуля. `prisma db push` створює її на живій БД, але нема одного
файлу, який робить порожню базу такою, як прод. Без цього немає ні тестової БД, ні можливості
безпечно додати `ruleset` пізніше.

Це **не міграції**. Це знімок: один `pg_dump --schema-only`, який перегенеровується щоразу, коли
схема змінюється. Джерело істини лишається базою — див. [Р2](../DECISIONS.md#р2-бд--джерело-істини-міграцій-немає).

## Готово, коли

## Кроки

**1. Зібрати схему в один файл.**

```bash
bunx prisma db pull            # переконатись, що дрейфу немає (станом на 2026-08-07 — немає)
# злити prisma/models/**/*.prisma + prisma/enums/*.prisma у prisma/schema.prisma
# оновити prisma.config.ts: schema: "./prisma/schema.prisma"
bunx prisma generate           # має пройти без помилок
```

Перед злиттям — виписати коментарі, які є в поточних файлах (`ArmorCategory.prisma` має
`// Special AC sources (seeded)` і подібні). `db pull` їх стирає, тож або переносимо в
`docs/`, або приймаємо втрату свідомо.

**2. Знімок схеми.**

```bash
pg_dump "$DATABASE_URL" --schema-only --no-owner --no-privileges > db/schema.sql
```

`--no-owner --no-privileges` — щоб файл накатувався на будь-яку локальну базу під будь-яким юзером.

**3. Скрипт.** У `package.json` (фактично зроблено — розходиться з початковим планом, причини нижче):

```json
"db:pull": "prisma db pull && prisma format && prisma generate && bun run db:dump",
"db:dump": "./scripts/db-dump.sh"
```

Замість `prettier --write` — рідний `prisma format`: prettier для `.prisma` усе одно потребує
окремого плагіна, а `prisma format` уже в комплекті й робить те саме.

`prisma-case-format` **не додано**. Він потрібен лише для нових таблиць і колонок, у проєкті не
встановлений і на цій схемі не перевірявся. Ставити неперевірений інструмент у гарячий шлях
`db:pull`, де він може перейменувати всю схему з першого прогону, — гірше за проблему, яку він
розв'язує. Ставити тоді, коли справді з'явиться нова таблиця, і перевіряти спершу на
`db-clone.sh ... _scratch`.

`db:dump` — окремий шелл-скрипт, а не однорядковий `pg_dump`, бо однорядковий не працює:
див. журнал (`?schema=public` в URL і версія клієнта).

**4. Перевірка.**

```bash
createdb spells_schema_check
psql spells_schema_check -f db/schema.sql
# має пройти без ERROR; далі порівняти набір таблиць із продом
dropdb spells_schema_check
```

**5. `db/changes/`.** Формат імені: `YYYY-MM-DD-короткий-опис.sql`. Кладемо туди рівно той SQL,
який реально виконали на базі. Ніхто його не переганяє автоматично.

## Ризики

- **`pg_dump` версії.** Локальний `pg_dump` має бути не старший за сервер, інакше дамп буде
  неповний або впаде. Перевірити `pg_dump --version` проти `SELECT version()`.
- **Розширення й типи.** Якщо на базі є щось поза Prisma (розширення, тригери, кастомні типи),
  воно потрапить у `schema.sql`, але не в `schema.prisma`. Це нормально і навіть добре — саме тому
  тестова БД піднімається з `schema.sql`, а не з Prisma.
- **Зведення в один файл — механічна операція.** Якщо в процесі захочеться «заодно причесати
  іменування» — не робити. Це O3.

**2026-08-07** — схему зведено в один файл. 91 файл (35 enum + 56 model) → `prisma/schema.prisma`,
`prisma.config.ts` переведено на `schema: "./prisma/schema.prisma"`. Заодно прибрано порожню
теку `prisma/migrations/`.

Злиття доведено без втрат механічно, а не на око: усі непорожні рядки декларацій до і після
злиття, нормалізовані по пробілах і відсортовані, збігаються рядок у рядок (1820 = 1820).
Варто повторювати цей прийом при будь-якій масовій механічній операції — він ловить те, чого
не видно у великому diff.

**2026-08-07 — сюрприз 1: `pg_dump` 14 проти сервера 16.** Ризик із розділу вище матеріалізувався
одразу: у PATH був `pg_dump` 14.20, сервер — PostgreSQL 16.1, дамп падає з
`aborting because of server version mismatch`. `postgresql@16` на машині стоїть, але Homebrew
тримає його unlinked, тож у PATH його немає. Тому `db-dump.sh` не викликає `pg_dump` з PATH, а
шукає придатний бінарник (PATH → `/opt/homebrew/opt/postgresql@*` → `libpq` → Postgres.app) і
падає з інструкцією, якщо не знайшов.

**2026-08-07 — сюрприз 2: `pg_dump` не їсть `DATABASE_URL` як є.** Prisma домішує в URL
`?schema=public`, а libpq такого параметра не знає: `psql: invalid URI query parameter: "schema"`.
Однорядковий `pg_dump "$DATABASE_URL"` з початкового плану не запрацював би взагалі.
`scripts/db-clone.sh` цю проблему вже вирішував, тож логіку чистки URL і перевірки версій винесено
в спільний `scripts/lib/pg.sh`, а `db-clone.sh` переведено на неї — замість другої копії.

**2026-08-07 — сюрприз 3: `bun run` не віддає `.env` шелл-скриптам.** Решта проєкту читає `.env`
через `dotenv` у `prisma.config.ts`, тому це раніше не спливало. `db-clone.sh` мав ту саму
приховану ваду й впав би так само. `load_dotenv` у `scripts/lib/pg.sh` вантажить `.env` тільки
якщо `DATABASE_URL` ще не виставлений, — у CI оточення має пріоритет.

**2026-08-07 — сюрприз 4: `pg_dump` ≥16.10 робить недетермінований дамп.** У кожен дамп вставляється
випадковий токен `\restrict …` / `\unrestrict …`, тож два поспіль однакові дампи дають diff у git,
і реальні зміни схеми в ньому тонуть. Лікується `--restrict-key`.

**Ключ мусить бути суто алфавітно-цифровим.** `--restrict-key=spells_schema_baseline` відкидається
з `pg_dump: error: invalid restrict key` — через підкреслення. Робочий варіант:
`spellsSchemaBaseline`.

**2026-08-08 — як цей баг проліз повз перевірку.** Перевірка детермінованості була написана так:

```bash
bun run db:dump >/dev/null 2>&1; cp db/schema.sql dump1.sql
bun run db:dump >/dev/null 2>&1; cp db/schema.sql dump2.sql
diff -q dump1.sql dump2.sql && echo "✅ детермінований"
```

`2>&1` сховав `invalid restrict key`, `;` замість `&&` дав прогону йти далі після падіння, а
`pg_dump` при помилці аргументів не чіпає цільовий файл — тож `db/schema.sql` обидва рази лишався
з попереднього, вдалого прогону. Два однакові файли, зелена галочка, нуль перевіреного.
**Мораль: у перевірці не глушити stderr і дивитися на код виходу, а не лише на результат.**
Тут це коштувало дешево, бо впало у власника при першому ж запуску. У KR1.4 (CI) таку перевірку
треба писати одразу з `set -o pipefail` і явним `rc`.

**2026-08-07 — що саме `db pull` стирає.** Формулювання в [Р2](../DECISIONS.md) («стирає коментарі»)
неточне. Перевірено на живому прогоні: `///` (doc-коментарі) інтроспекція **зберігає** — усі 23
на місці. Стираються тільки звичайні `//`; їх було два, обидва змістовні, обидва повернуто як `///`:
- `ArmorCategory` — позначка, звідки в енумі починається не броня, а джерела AC;
- `Pers.additionalSaveProficiencies` — «попри назву, не додаткові, а базові».

Практичний висновок: **усе, що має пережити наступний pull, пишеться як `///`.** Це єдиний виняток
із правила «`schema.prisma` руками не чіпаємо», і він внесений у CLAUDE.md.

**2026-08-07 — знахідка: `prisma-json-types-generator` встановлений наполовину.** У схемі є 23
анотації виду `/// [RaceASI]`, `/// [SkillProficiencies]`, і є готовий
`src/lib/types/prisma-json.d.ts` з `declare global { namespace PrismaJson { … } }` — тобто повна
обв'язка під `prisma-json-types-generator`. Але **самого генератора немає ні в `package.json`, ні

Не чіпав: доведення генератора до кінця змінює типи по всьому коду — це O3, не O1.
Анотації збережено недоторканими саме тому, що вони ще знадобляться.

**2026-08-08 — два баги в `find_client_binary`, обидва про шел, не про Postgres.** Перша версія
перебирала кандидатів glob-ом просто в списку `for`. Під bash це коректно (незматчений glob
лишається літералом і не проходить `[[ -x ]]`), але якщо `pg.sh` заsource'ити з інтерактивного
zsh — незматчений `/usr/local/opt/postgresql@*` валить весь виклик. Друга версія лікувала це
конвеєром із `head -1` — і зламала гірше: під `set -o pipefail` (а він стоїть в обох скриптах)
`head` закриває канал, апстрім отримує SIGPIPE, конвеєр повертає ненульовий код, і скрипт падає
**навіть коли бінарник знайдено**. Робочий варіант — без конвеєра взагалі: кандидати збираються в
рядок через command substitution, далі звичайний `while … <<< "$candidates"`.
